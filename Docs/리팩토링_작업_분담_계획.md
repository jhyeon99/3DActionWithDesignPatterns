# 2~3주차 리팩토링 작업 분담 계획 (5인)

> **목적:** 1주차 구현(Git 기록)과 패턴 담당표를 모두 고려해, 서로의 작업이 겹치지 않고 **순서와 무관하게** 진행되도록 나눈다.
> **기준 문서:** `담당 패턴별 구현 래퍼런스 및 추가 패턴.md`(§3, §9, §10), 패턴 담당표

## 0. 담당 매핑

| 담당 | 이름 | 패턴 | 한 줄 책임 |
|---|---|---|---|
| A | 송재욱 | State(플레이어), Command | 플레이어 상태와 입력 처리 |
| B | 김민석 | Object Pool, Factory | 투사체·적·구슬 생성/재사용 |
| C | 장준혁 | Strategy, State(적) | 적 행동 교체와 상태 전환 |
| D | 정재윤 | Decorator, Chain of Responsibility | 스탯/버프 계산과 피해 처리 |
| E | 송재현 | Observer, Type Object, Service Locator | 이벤트·데이터·서비스, 진행 흐름·UI |

> **Factory 소유 결정:** 문서 §3은 B가 적·투사체 Factory를, §10은 C가 몬스터 Factory를 맡는 것으로 갈린다. 패턴 담당표를 따라 **김민석(B)이 적·투사체 Factory/Pool을 모두 소유**하고, 장준혁(C)은 AI만 맡는다.

## 1. 핵심 원칙

1. **레거시 파일은 한 명만 소유한다.** 다른 사람은 인터페이스로만 접근한다.
2. **Phase 1은 새 파일 추가만 한다.** 1주차 파일은 수정하지 않는다.
3. **모든 외부 계약에 Legacy/Null 기본 구현을 둔다.** 상대 구현이 없어도 빌드·동작하므로 머지 순서가 자유롭다.
4. **모든 작업자는 `Test_<패턴>` 씬에서 Fake로 검증한다.**
5. **모든 PR은 기준선 대비 수치를 첨부한다.**

| 파일 | 건드리려는 사람 | 단일 소유자 | 다른 담당의 접근 방법 |
|---|---|---|---|
| `GameManager.cs` (UI·웨이브·증강·점수) | 송재현, 정재윤, 김민석 | **송재현** | `IEnemySpawner`, `IUpgradeApplier` 구현체만 제공 |
| `PlayerFire.cs` (타게팅·쿨다운·탄 생성·스탯) | 송재욱, 김민석, 정재윤 | **김민석** | 타게팅은 송재욱 쪽으로 이동, 스탯은 `IStatProvider`로 읽음 |
| `PlayerBullet.cs` | 김민석, 정재윤 | **김민석** | 피해는 `IDamageable` 호출 하나로 정재윤에게 위임 |
| `Player.cs` (상태·HP·방어·디버프·HP바) | 송재욱, 정재윤, 송재현 | **Phase 0에서 3개로 분리** | Phase 0의 3번 참고 |

| `Exp.cs` | 김민석, 송재현 | **김민석** | 획득 이벤트 발행 한 줄만 `IGameEventBus` 사용 |
| `DebugStats` / `DebugOverlay` | 전원 | **송재현** | 다른 사람은 줄 추가만 허용 |

## 3. 작업 순서

### Phase 0. 공통 준비 (1명이 하루 안에 완료, 이후 전원 분기)

1. **기준선 측정:** 디버그 오버레이에서 `F5`(50마리)로 60초간 FPS, worst ms, GC/s, created/destroyed를 기록해 표로 저장한다.
2. **`Contracts/` 폴더 확정:**
   - ID: `EntityId`, `EnemyId`, `WeaponId`, `UpgradeId`
   - DTO: `AttackIntent`, `HitRequest`, `DamageResult`, `EnemySpec`, `WeaponSpec`, `UpgradeSpec`
   - 포트: `IAttackSink`, `IHitSink`, `IEnemySpawner`, `IEnemyRegistry`, `IDamageable`, `IHealthRegistry`, `IStatProvider`, `IStatusEffectService`, `IUpgradeApplier`, `IGameEventBus`, `IClock`
   - 각 포트에 **Legacy/Null 기본 구현** 포함 (예: `IEnemyRegistry` 기본값 = `FindObjectsByType`)
3. **동작 불변의 기계적 분리** (이 PR만 파일을 가로질러 수정):
   - `Player.cs` → `Player`(상태·이동 연결) / `PlayerHealth`(HP·방어·디버프 타이머) / `PlayerHpView`(OnGUI 바)
   - 플레이어·몬스터가 `IDamageable` 구현, `PlayerBullet`의 3중 `TryGetComponent`를 단일 호출로 교체
   - `PlayerFire.Fire()`를 `FindTarget` / `SpawnBullet` / `BuildDamage`로 메서드 분리
4. **소유권 표와 테스트 씬 규칙 확정**

### Phase 1. 병렬 개발 (새 파일만 추가, 레거시 수정 금지)

| 담당 | 만들 것 | 대체물(Fake) | 완료 기준 |
|---|---|---|---|
| **송재욱** | 플레이어 FSM(Alive/HitStun/Dead + Idle/Moving), `InputAdapter`, `AttackCommand`/`DashCommand`, `CommandExecutor`, 키 매핑 테이블, 자동 타게팅 → `AttackCommand` | Fake `IAttackSink`, 가짜 피격 호출 | 대기→이동→자동 공격→피격→사망 상태가 화면/로그에 표시, 키 매핑을 바꿔도 동작 |
| **김민석** | 제네릭 `Pool` + `IPoolable`, 투사체/적/구슬 풀, `ProjectileFactory`/`EnemyFactory`(ID로 종류 선택), 풀 카운터를 `DebugStats`에 연결 | 기본 도형, Fake `IHitSink` | 100발 발사해도 created 증가 없음, ID/데이터만 넘기면 다른 적·투사체 생성 |
| **장준혁** | `IMovementStrategy`/`IAttackStrategy`(추적, **순찰·원거리 신규**, 돌진), 적 FSM(순찰→추적→공격→사망, 예고, 기절), 이후 보스 2페이즈 | Fake Body/Target, 가짜 HP 변경 | 같은 적에 전략만 바꿔 끼워 움직임이 달라지고, 상황에 따라 상태 전환 |
| **정재윤** | `BaseStats` + Decorator(고정/배율/공속/관통), `BuffInstance`(Unique/Stack/Refresh), `HealthStore`, 피해 Chain(중복타격→공격→방어→보호막→HP), 단계별 로그, 상태이상 서비스(기존 기절/이감/공감 이관) | 수동 Tick, 메모리 HealthStore | 버프 여러 개 겹치고 해제 시 정확히 복원, 최종 피해가 단계별 로그로 표시 |
| **송재현** | `GameEventBus` + 이벤트, `ServiceLocator` + `GameBootstrap`, Definition SO + 검증 + Spec 변환(기존 몬스터 수치 이관), `ScoreService`/`WaveDirector`를 GameManager에서 분리, HUD 구독자 | 수동 `Publish`, Fake `IClock` | 처치 이벤트 하나로 점수·UI·로그 동시 반영, SO 값 변경으로 적 수치 교체, 서비스 등록 후 다른 스크립트에서 조회 |

### Phase 2. 전환 (각자 자기 레거시 파일만 교체, 머지 순서 무관)

| 담당 | 교체할 파일 |
|---|---|
| 송재욱 | `Player.cs`, `PlayerMove.cs` |
| 김민석 | `PlayerFire.cs`, `PlayerBullet.cs`, `Exp.cs` |
| 장준혁 | `Monster/*.cs` |
| 정재윤 | `PlayerHealth.cs`, `Combat/` 전체 |
| 송재현 | `GameManager.cs`, UI (`SpawnMonster`의 `Instantiate` → `IEnemySpawner`, `ApplyUpgrade` → `IUpgradeApplier`) |

**권장 통합 순서** (문서 §10-5, 강제 아님):

1. 송재욱 + 김민석: `AttackIntent` → 투사체 생성/풀
2. 김민석 + 장준혁 + 정재윤: 피격 → `DamageResult` → 사망 → 풀 반환
3. 송재현: 이벤트 버스, HUD, 웨이브, 서비스 연결

| 지표 | 해당 패턴 | 측정 방법 |

## 5. 순서 의존이 실제로 남는 곳

| 항목 | 이유 | 대응 |
|---|---|---|
| Phase 0의 Contracts | 전원이 이 위에서 시작 | 가장 먼저, 0.5~1일로 시간 제한 |
| Contract 변경 | 필드 변경은 소비자 전원 영향 | 소유자가 변경안을 올리고 소비 담당 전원 확인, 임의 복사본 금지 |
| `GameBootstrap` 연결 | 모든 구현체를 연결하는 마지막 단계 | 그 전까지 각자 Fake로 검증 |

## 6. 브랜치/PR 규칙

- Phase 1 PR: 새 파일 추가만 (레거시 수정 시 리뷰에서 반려)
- Phase 2 PR: 자기 소유 파일만 수정, 기준선 대비 수치 첨부
