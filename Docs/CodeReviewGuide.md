# GEMINI.md — 코드 리뷰 기준

이 저장소는 5명이 게임 개발 디자인 패턴을 나눠 구현하고, 이를 병합해 하나의 Unity 3D 탑다운 액션 게임을 만드는 학습 프로젝트입니다.
리뷰의 1순위는 **디자인 패턴이 의도대로, 올바르게 적용되었는지**입니다.

## 프로젝트 구조

- C# 스크립트: `Assets/02.Scripts/`
- 게임 로직은 순수 C# 클래스로 작성하고, `MonoBehaviour`는 화면 표시와 Unity 연결에만 사용하는 것을 원칙으로 합니다.
- 다른 담당자의 모듈은 합의된 인터페이스로만 접근합니다. 구현 클래스를 직접 참조하면 지적해 주세요.

## 사용하는 디자인 패턴과 확인할 점

| 패턴 | 확인할 점 |
|---|---|
| State | 상태 전환이 상태 클래스 안에서 일관되게 처리되는가. `Enter` / `Update` / `Exit` 누락이나, 상태 밖에서 `switch`·`if`로 분기하는 코드가 남아 있지 않은가 |
| Command | 입력과 실행이 분리되어 있는가. 명령 객체가 실행에 필요한 정보를 스스로 갖고 있는가 |
| Object Pool | 반환 시 상태(위치, 체력, 속도, 코루틴, 이벤트 구독 등)를 초기화하는가. 반환한 객체를 계속 참조하거나 이중 반환하지 않는가. 풀 밖에서 `Instantiate` / `Destroy`를 직접 호출하지 않는가 |
| Factory | 생성 로직이 팩토리에 모여 있는가. 호출하는 쪽이 구체 클래스를 몰라도 되는가 |
| Strategy | 전략 교체가 인터페이스를 통해 이루어지는가. 전략 클래스가 특정 적이나 상황에 과하게 결합되어 있지 않은가 |
| Decorator | 감싸는 순서와 제거가 올바르게 동작하는가. 버프 제거 시 원래 값으로 복원되는가 |
| Chain of Responsibility | 각 처리 단계가 하나의 책임만 갖는가. 다음 단계 호출 누락이나 순서 의존 버그가 없는가 |
| Observer | **구독한 이벤트를 반드시 해제하는가** (`OnEnable`/`OnDisable`, `OnDestroy`). 이벤트 호출 시 null 체크를 하는가. 발행자가 구독자를 직접 알지 않는가 |
| Type Object (ScriptableObject) | 런타임에 ScriptableObject 원본 값을 수정하지 않는가. 공유 데이터와 인스턴스별 상태가 분리되어 있는가 |
| Service Locator | 서비스를 등록하기 전에 사용하는 경우가 없는가. 남용되어 사실상 전역 변수처럼 쓰이고 있지 않은가 |

## Unity 관련 확인 사항

- `Update` 등 매 프레임 호출되는 곳의 불필요한 메모리 할당 (`new`, LINQ, 문자열 연결, 박싱, `GetComponent` 반복 호출)
- `Awake` / `Start` / `OnEnable` 실행 순서에 의존하는 초기화 버그
- 비활성화되거나 파괴된 오브젝트 참조 (`MissingReferenceException` 가능성)
- 코루틴이 오브젝트 비활성화·풀 반환 후에도 남아 있는 경우
- 물리 처리를 `Update`에서 하는 경우 (`FixedUpdate` 권장)

## 리뷰하지 않을 것

- 디자인 패턴 적용을 위해 의도적으로 나눈 인터페이스·클래스를 "과하다"고 평가하는 것
- 네이밍, 중괄호 위치 같은 단순 취향 차이
- 변경되지 않은 코드에 대한 대규모 리팩터링 제안
